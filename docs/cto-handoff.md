## 6. データモデル(SSOT)

`video.json`(zod検証: `src/schema.ts`)。要点:

- `meta`: fps=60, 1080×1920, speakerColors, フォント, **speechRateApplied: 1.2**(話速適用済みマーカー、再適用ガード)
- `scenes[] > cuts[]`:
  - `dialogue[]`: {id(例 s1c2-01), speaker, text, emotion, speed, pauseAfterSec}
  - `camera`: {shot, parallax{zoom,panX,panY}, easing}
  - `board`: {visible, actions[{element(circle/line/arrow/label/erase), atLineId, offsetSec, drawDurationSec}]}
  - `chars[]`: {speaker, pose(stand/point/think/tea/tablet), position(left/right/center), scale, visible}
  - `subtitle.lines[]`: {lineId, displayText(改行済み), emphasis, ruby}
  - `sound`: {bgmCue(none/main-soft/main-warm/outro), ambience(garden-day/garden-evening/none), sfx[{file, atSec, gainDb, durationSec?}]}
  - `fixedDurationSec`(無音カット) / `fgLayers[]`("teacup:x,y,w" / "steam:x,y" 形式)

### 派生データ(生成物、手編集禁止)
- `public/audio-manifest.json`: [{lineId, file, durationMs}] — tts.ts生成、**カット尺の唯一の根拠**
- `public/alignment/*.json`: 文字タイムスタンプ(1.2倍速適用済み)
- `src/patch-config.json` = `public/assets/cutout/mouth/patch-config.json`: 口パク配置情報(mouthpatch.py生成、**両方に書かれる。同期必須**)

### タイミング規則(timing.ts、mix.tsも同一規則を複製)
- セリフありカット尺 = HEAD(0.35s) + Σ(音声実測尺 + pauseAfterSec) + TAIL(0.55s)
- セリフなしカット尺 = fixedDurationSec
- 総尺 303.9秒 / 18,236フレーム。**この規則を変える場合は timing.ts と mix.ts の両方を変更**(単一実装への統合はPM判断の技術的負債、§15)

## 7. データフロー(コマンド → 入出力)

| コマンド | 入力 | 出力 | 再実行が必要になる契機 |
|---|---|---|---|
| `npm run tts` | video.json(dialogue) | public/audio/*.mp3, audio-manifest.json | セリフ・声・話速変更 |
| `python pipeline/align.py` | audio/*.mp3 | alignment/*.json | 音声再生成後 |
| `python pipeline/fixbg.py` | assets/bg/_orig/ | assets/bg/(小黒板消し込み) | 背景素材差し替え |
| `python pipeline/cutout.py` | assets/{chars,bg,fx} | assets/cutout/ | 素材差し替え・fixbg後 |
| `python pipeline/mouthpatch.py` | cutout/chars | cutout/mouth/, patch-config.json×2 | キャラ素材・座標変更 |
| `node pipeline/sfxcue.mjs` | video.json(board), manifest | video.json(sound.sfx) 上書き | 黒板演出変更 |
| `node pipeline/typeset.mjs` | 内蔵の組版マップ | video.json(subtitle) 上書き | セリフ変更 |
| `npm run mix` | video.json, manifest, audio/, bgm/, ambience/, sfx/ | out/master-audio.wav | 音まわり一切の変更 |
| `npx remotion render Main out/master.mp4 --codec h264 --crf 16` | 全て | out/master.mp4 | 映像まわり一切の変更 |
| `npm run encode` | out/master.mp4 + out/master-audio.wav | out/final-master.mp4 | render/mix後 |

**重要**: sfxcue.mjs と typeset.mjs は該当フィールドを毎回ゼロから再構築する(冪等)。video.jsonの当該フィールドを手編集しても次回実行で消える。恒久変更はスクリプト内の定義を変えること。

## 8. 品質要件・非機能要件

- **音**: 行単位 -18 LUFS(TTS後loudnorm済み)、BGM基準 -34 LUFS(セリフ中サイドチェインで約-8dB沈む: threshold 0.02/ratio 6/attack 120/release 600)、環境音 -40、SFX -26+gainDb、マスター2パスloudnorm -14/-1.5/LRA 11
- **映像**: レンダーは h264 crf16(視覚的無損失級)。最終muxは映像コピー+AAC 320k+faststart
- **決定性**: 全アニメーションはフレーム駆動(`useCurrentFrame`)。乱数は `mulberry32(hashSeed(id))` でシード固定。同一入力→同一出力
- **再現性**: 生成物はすべて `out/` と `public/`配下の派生ディレクトリ。ソース素材の原本は `_orig/` 退避(fixbgは冪等: 再実行時 _orig から作り直す)
- **性能**: 全編レンダーは数十分〜(60fps×18,236f、CPUコア数依存。`--concurrency` はコア数超過でエラー)。QCイテレーションは `remotion still` の単フレーム検分を基本とする(1枚≒40秒、うちバンドル30秒)

## 9. 技術選定理由(要約)

- **Remotion 4.x**: React宣言的合成+決定的フレームレンダリング。Studio/still による部分検証が可能
- **Fish Audio s2.1-pro-free**: 日本語品質と無料枠。**1リクエスト500文字未満**制約→行単位生成で回避
- **stable-ts**: 文字レベルタイムスタンプが取れる唯一の実用的ローカル手段。viseme(あ/い/う/え/お+閉口)とカラオケ字幕の両方の根拠
- **ffmpeg直叩き(mix.ts がfiltergraph生成)**: DAW不使用で決定的ミックス。フィルタグラフはファイル出力(`out/mix-filter.txt`)しデバッグ可能
- **不採用**: RIFE/FILM(ネイティブ60fpsに補間は劣化のみ)、CodeFormer/GFPGAN(実写向け)、Live2D(リギング自動化不能)、HDR/AV1(YouTube再エンコード前提ではH.264高ビットレートが最適)

## 10. AIエージェント開発方針(各種エンジニアリング方針)

- **Prompt Engineering**: エージェント定義は `agents/*.md` に責務・入出力スキーマ・禁止事項を明文化。プロンプトに座標や実測値を直書きせず、video.json/patch-config.json を参照させる
- **Context Engineering**: 作業者エージェントには「担当フィールドのスキーマ+当該カットのJSON断片+関連アセットのパス」のみ渡す。video.json全文の投入は不要(45行/42カットで肥大)
- **Harness Engineering**: 創造的判断の出力は必ず「video.jsonへの書き戻し」に限定し、レンダリングコード直編集をさせない。機械変換はスクリプト化して冪等にする(sfxcue/typesetが先例)
- **Loop Engineering**: QCループは「still検分 → video.json/座標定義修正 → 該当パイプラインのみ再実行 → 再検分」。全編再レンダーは修正が出尽くしてから1回。**PMはマイルストーン境界でのみ確認、細粒度ポーリング禁止**(運用ルール)
- **State Engineering**: 状態はすべてファイル(video.json+派生物)。エージェント間のメッセージで状態を運ばない。適用済み変換はマーカーで冪等化(例: meta.speechRateApplied)

## 13. ADR(Architecture Decision Records)

- **ADR-1 話速1.2倍は再合成せずatempoで実現**: ユーザー承認済み音声の質感を保持。alignmentは1/1.2でスケール、原本は `public/audio/_orig-1.0x/` 退避、`meta.speechRateApplied` で再適用ガード
- **ADR-2 口パクは「口だけパッチ」方式**: AI生成の口形差分はstandと位置・スケール不一致→差分から口を楕円フェザーで切り出し、1/faceScaleで正規化して260×260のstand座標系パッチ化(mouthpatch.py)。非standポーズ21カットにも per-pose {anchor,scale} で同一パッチを流用
- **ADR-3 クロマキーは色距離の決定的処理(rembg不採用)**: 素材がマゼンタ背景納品のため。`(min(r,b)-g)/255` キー+縁ディスピル。**元アルファとの乗算合成必須**(夕方背景の青縁は元々アルファ0で、RGB変換でアルファを捨てて青が出た事故の教訓)
- **ADR-4 背景の小黒板は決定的インペイントで除去**: 生成AIによる修正は再現性がないため不採用。昼=マゼンタ穴延長+柱縦タイル+畳の左右donor水平ストレッチ。夕=照明マップ転写(上下帯の列平均を縦補間した光×donorテクスチャのディテール分離)で光条を保存
- **ADR-5 SFXキューは黒板アクションから自動導出**: 手打ちでなくboard.actionsのストローク(circle/line/arrow)から機械生成。labelとeraseは無音。演出SFX(茶・タブレット・チョーク置き)のみ定義テーブル
- **ADR-6 ミックスはレンダー音声を使わずソースから構築**: Remotionはセリフのみ再生。mix.tsがセリフmp3+BGM+環境音+SFXを直接タイムライン合成→世代劣化なし、レンダーと並行実行可能
- **ADR-7 2.5D深度パララックスは延期**: 品質寄与に対しDepth Anything V2導入コストが高く、カメラpan/zoomで動きは確保できている。将来 `pipeline/depth.py` + `DepthParallax.tsx` を追加する設計余地は維持
- **ADR-8 黒板は素材画像の盤面実測矩形へSVGを射影**: 素材(1920×1280)の盤面(428,262)-(1488,1026)を表示BOARD_RECT(100,300,880,634)に合わせ、ChalkBoardの900×640 viewBoxを引き伸ばし(歪み~1.3%、許容)
- **ADR-9 トゥルーピークの検収基準は納品AACの ≤-1.0 dBTP のみ。WAVの-1.5はmix内部ターゲット**: mix.tsのloudnormはTP -1.5をターゲットにリミットするが、loudnormの内部192kHz処理後に48kHzへ書き出すリサンプリングで約0.1dBのオーバーシュートが発生する(実測: WAV -1.4 / AAC -1.4 dBTP)。これは処理チェーンの既知の性質であり、-1.5というターゲットはこのオーバーシュートと非可逆変換分を吸収して納品基準(YouTube推奨 ≤-1.0)を確実に満たすためのヘッドルームである。したがって検収ゲートは**納品AACの ≤-1.0 のみ**とし、WAVは参考測定(-1.3を超えたらmixパラメータ見直し)とする。経緯: 初版では§2(-1.5)とqc-checklist(-1.0)が測定対象を明記せず矛盾。PM自己検証で顕在化。CTOの当初の裁定説明「AAC変換によるオーバーシュート」も実測で誤りと判明(WAV段階で既に-1.4)し、本ADRで訂正(2026-07-21)。教訓§17.2-1「測っただけが証拠」はCTO自身にも適用された

- 中間生成物も全て存在: `out/master.mp4`(レンダー原本)、`out/master-audio.wav`、`out/premaster.wav`、`out/mix-filter.txt`
- 全編レンダー実測: 約35分(このマシン、concurrency自動)。起動失敗2回の教訓は§17.1-8参照

### PMが計画・完遂すべき残作業(スコープ全量)
1. **QC巡回**(唯一の大物): `out/final-master.mp4` を対象に、`docs/qc-checklist.md` 準拠で全42カット検分 → 修正指示を video.json / 座標定義(mouthpatch.py の CONFIG/POSES、fixbg.py のパラメータ)へ反映 → §7の対応表に従い**該当工程のみ**再実行 → 再検分。修正が出尽くしてから全編レンダー+encodeを1回。ループ設計は§10 Loop Engineering・見積りは§17.3
   - 必須判定項目: §15既知問題1〜3(ミケ口パッチのハロー/s1c1右柱の埋め跡/先生teaポーズの口被覆)。いずれも「実寸視聴で知覚されるか」で採否を判定し、不合格のみ修正する
   - 検分は動画再生+代表フレームstill併用。stillは `npx remotion still Main --frame=N --output=out/qc-<cut>.png`(タイミング参照値は§14)
2. **outro.mp3 反映**(発注者の配置待ち、ブロッカー): 配置確認後 `npm run mix && npm run encode` のみ(レンダー不要、数分)。mix実行ログに `[warn] BGM 未配置` が**出ないこと**を完了条件にする
3. **納品**: final-master.mp4 + 検収報告(§2の6項目それぞれの実測値・判定を明記)。ラウドネス再実測は encode が自動出力する(`final: ... I=... LUFS`)
4. **任意(発注者と要調整、デフォルトはやらない)**: 深度パララックス(ADR-7)、ミケ口パッチのハロー低減チューニング、zodバージョン負債解消

## 17. CTOの実装経験からの教訓(PM・作業者エージェントへ)

本プロジェクトはCTO自身が全工程を一度実装して検証済みである。以下は**実際に起きた失敗**とその根本原因、およびPMがタスク設計・エージェント指示・完了条件に反映すべき一般化した教訓である。抽象論ではなく全て実例に基づく。

### 17.1 事故事例と根本原因

| # | 事故 | 根本原因 | 対処した方法 |
|---|---|---|---|
| 1 | ミケの目の座標を300px誤読(マゼンタ背景を目と誤認) | グリッド付き画像の**目視のみ**で座標を確定した | ピクセル色プローブ(np配列の実値サンプリング)で裏取りしてから確定 |
| 2 | ミケの閉眼ボックスを2度誤設定(黒い毛柄を目と誤認/ヒゲをまつ毛と誤認) | AI生成画像は解剖学的な想定が通用しない(三毛柄・顔の向き) | 変更のたびに合成プレビューシート(コンタクトシート)を生成して目視検収 |
| 3 | 「非standポーズで話すカットは無い」と誤判定→21カットの口パク対応を見落としかけた | zodのdefault値(`visible:true`)は**生JSONのrequireでは存在しない**のに `ch.visible &&` で判定した | `visible !== false` に修正。以後、スコープ調査はスキーマパース後のデータで行う |
| 4 | 夕方カットの背景が真っ青になった | cutout.pyが `convert("RGB")` で**元画像のアルファを破棄**していた。夕方素材だけ縁が「透過(RGB=青)」だった | 元アルファとキーのmin合成に修正 |
| 5 | 夕方背景に昼用の消し込み座標を適用し、茶色い矩形が出た | 「昼と夕は同じ部屋・同じカメラ」という**手順書の指定を素材が満たしている**と検証せず仮定した | 素材ごとに構図を実測し、夕方専用の処理を別実装 |
| 6 | 戸口の右境界を868pxと誤推定し、壁に矩形の欠けが出た | グリッド画像からの外挿。実測せずに埋め範囲を決めた | 走査スクリプトで境界を実測(823px)してから再実行 |
| 7 | インペイントが5回やり直しになった(ミラータイルの蝶模様/donor帯への棚・縁線の混入/ストレッチによる質感消失/半透過画素の混入) | 畳・光条・縁線という複数の構造を一手法で埋めようとした | 構造ごとに手法を分離(縦構造=縦タイル、水平線=水平ストレッチ、照明=ライティングマップ転写)し、毎回**表示スケールで**目視検収 |
| 8 | 全編レンダーが2回起動失敗(1回目: `--concurrency 8` がコア数超過で即死/2回目: バックグラウンドシェルのcwdがプロジェクト外でnpx解決失敗)。しかも**完了通知はexit 0だった** | 長時間ジョブの起動成功を確認せず放置した | 起動直後に出力ファイル生成 or プロセス存在を確認してから待機する |
| 9 | `remotion still NekoTera` が失敗 | コンポジションIDの思い込み(正: `Main`) | エラーメッセージの候補一覧を読む(エラーが正解を教えてくれる) |
| 10 | PowerShellでJSONを読もうとして文字化け/Pythonのf文字列パスで `\f` がフォームフィードになりOSError | Windows固有の罠(PS5.1のUTF-8、バックスラッシュエスケープ) | JSON操作はNode/Python、パスは os.path.join に統一 |

### 17.2 一般化した教訓(PMがタスク設計に反映すべきもの)

1. **「見た」は証拠にならない。「測った」だけが証拠**(事例1,2,5,6)。画像座標を扱うタスクの完了条件には必ず「ピクセル値サンプリングによる裏取り」と「合成プレビューの添付」を含めること。作業者エージェントへの指示にこれを明記する。
2. **ゼロ件・異常なし という調査結果ほど疑う**(事例3)。スコープ調査で「対象なし」が出たら、判定ロジック自体の検証を完了条件に含める。ここを誤ると後工程で21カット分の手戻りになるところだった。
3. **納品素材の一様性を仮定しない**(事例4,5)。手順書に「同じ構図で」と書いても、その通りに来るとは限らない。**素材ごとに**パイプラインを通し、素材ごとに検分するタスク構造にする(代表1枚の確認で全数を合格にしない)。
4. **検証は必ず最終表示系で行う**(事例7,11)。ピクセル等倍のズームで合格でも表示スケールで破綻する(逆もある)。字幕はテキストではなくレンダリング結果で、画像は合成後のスチルで判定する。
5. **反復前提の工程と一発で決まる工程を区別して計画する**(事例7)。決定的インペイントや座標合わせは**3〜5回の目視ループが正常**であり、1回で終わる前提の計画は破綻する。逆にmix/encodeのような計測駆動の工程は1回で決まる。QCループの回数バッファはこの区別に基づいて置くこと。
6. **長時間ジョブは「起動確認」と「完了確認」を別タスクにする**(事例8)。バックグラウンド実行の通知やexit codeは信用しない。起動直後の生存確認、完了後の成果物実在確認(ファイルサイズ・尺・ラウドネス実測)を独立したチェック項目にする。
7. **高速な検証手段に投資してから量産する**。本件では「still 1枚40秒」のループを確立してから修正を回した。全編レンダー(数十分〜)でしか検証できない状態で修正を始めてはならない。PMは「検証手段の確立」を最初のタスクとして明示すること。
8. **冪等性とバックアップが反復を可能にする**(事例7が5回やり直せた理由)。素材を上書きする処理は必ず `_orig/` 退避+再実行時は退避から再構築、適用済み変換にはマーカー(`speechRateApplied`)。作業者エージェントに新しい変換スクリプトを書かせる際は、この2点を受け入れ条件にする。
9. **エラーメッセージと計測値を先に読む**(事例6,9)。推測で再試行する前に、エラーが提示する候補・実測スクリプトの数値を取る。「測ってから切る」は座標に限らず全工程に適用される。
10. **Windows環境の罠は工程設計で回避する**(事例10)。シェル・エンコーディング・パス処理の選択を作業者の裁量に任せず、§11のコーディング方針を指示テンプレートに含める。

### 17.3 見積り・ループ設計への実測データ

- 座標実測1回(グリッド生成+プローブ+判定): 数分。誤読からのリカバリ: 1〜2イテレーション
- 背景インペイント: 5イテレーション(手法転換2回を含む)で収束。「構造の混在」に気づくまでが長い
- still検分: 1枚≒40秒(バンドル30秒+レンダー10秒)。同一修正の検証は2〜3枚(昼/夕/該当カット)が目安
- mix: フル実行≒30秒、ラウドネスは2パスで一発着地(-14.0)。音工程は映像より予測可能性が高い
- 全編レンダー: 数十分規模(バックグラウンド必須、起動確認を忘れない)

### 17.4 PMへの最重要メッセージ

このシステムの品質は「エージェントの賢さ」ではなく**検証ループの設計**で決まった。失敗11件のうち10件は「検証を省略した仮定」が原因であり、能力不足が原因のものは1つもない。タスクを割り当てる際は、作業内容よりも**完了条件(何をどう測って合格とするか)**の記述に時間を使うこと。
