# p1-d0 · mi3san に決めていただくこと

**担当:** Orbit が提示、mi3san が決定
**性質:** 実装 packet ではない

## この文書の書き方について

初版は、内部実装を知っている前提の用語で8件を並べていた。**内部を見ていない読み手が判断できない形**であり、
さらに**半分は本来 Orbit が決めるべき技術的選択**を owner 判断として押し付けていた。

`AGENTS.md` が定めるオーナーの判断領域は **実映像・外部取得の承認・予算** である。モジュール構成ではない。
そこで本版では次のように分けた。

- **第1部 — あなたが決めること**（4件）。専門用語なしで、何が変わるかだけを書く
- **第2部 — 私が決めたこと**（4件）。技術的選択。報告であって依頼ではない。異論があれば覆せる

# 第1部 · あなたが決めること

## ① レンダリングするプログラムのネット遮断設定 🔴

**お願いしたいこと。** あなたのPCで、次の2つのプログラムが**インターネットに出ないようにする設定**をしてください。

| プログラム | 何に使うか |
| --- | --- |
| `chrome-headless-shell.exe`（`node_modules/.remotion/chrome-headless-shell/win64/chrome-headless-shell-win64/` の中） | 方式A の映像を作る |
| `blender.exe`（`M3-01` で入れた Blender **4.5.0** の方。Blender 5.2 ではありません） | 方式D と E の映像を作る |

**なぜ必要か。** 以前、映像を作る途中でフォントを勝手にネットから取りに行っていたことがありました（AP-009）。
外部から何も取ってこない状態で作った、と言えるようにするためです。

**なぜ私にできないか。** これはPCのセキュリティ設定の変更です。私の動作規約で禁止されています。

**やり方。** Windows Defender ファイアウォールで、上の2つそれぞれに次の規則を作ってください。
作成方法（GUI でも管理者 PowerShell でも）はお任せします。

```
方向      : 送信（Outbound）
動作      : ブロック
プログラム : 上記の絶対パス
リモート   : すべて
有効      : はい
```

**終わったら。** 次を実行すると、設定できているかを私が確認して記録します。

```bash
npm run m3:record-network-enforcement
```

**これをしないと。** 4方式すべての映像制作が始められません。ここが今の最大の詰まりです。

## ② 各テストの長さ 🔴

**状況。** 比較のために6種類の動きをテストします。

| テスト | 何を見るか |
| --- | --- |
| T0 | 止まっているときの安定感 |
| T1 | 口をだんだん開ける |
| T3 | **開けた口を途中で閉じる**（歯や口の中が隠れるか） |
| T6 | 2つの動きを同時にやる |
| T7 | 顔を左右15度・上下10度まで振る |
| T9 | 速さを変える・止める・逆向きに動かす |

**決めていただきたいこと。** これを**1本の動画（約10秒）にまとめる**と、1テストあたり**約1.7秒**になります。

- **1.7秒で判断できそう** → 1本にまとめます
- **短すぎる** → テストごとに別の動画にします（6本 × 4方式 = 24本）

**判断材料。** T9（速さを変える・止める・逆向き）は、1.7秒だと窮屈かもしれません。
一方、本数が増えると見る側の手間も増えます。**あなたが見比べやすい方**を選んでください。

---

## ③ 上限「40人時」を、AIが作った分にどう当てはめるか 🟡

**状況。** あなたは以前、各方式の制作上限を**合計40人時**と決めました（`M3-03`）。
これは**人間が手で作る前提**の数字でした。

実際には5方式ともAIが作りました。**人間が何時間かけたかに相当する数字は存在しません。**
適当な数字を入れるとコスト比較が嘘になるので、記録は**空欄**にしてあります。

**決めていただきたいこと。** どう扱いますか。

| 案 | 内容 |
| --- | --- |
| 数えない | 人時はコスト比較の軸から外す。他の軸（計算資源・修正の手間）で比べる |
| 実時間で代用 | かかった実時間を記録する。ただし人間の作業時間とは意味が違う |
| 別軸にする | 「人間なら何時間」と「AIでいくら」を別々に並べる |

**いつまでに。** 方式を比較する表（`M3-12`）を作る前です。急ぎではありません。

---

## ④ バグ修正を「作り直し回数」に数えるか 🟡

**状況。** 方式C で、**あなたが承認した操作範囲の内側で、口の輪郭が自分自身と交差する**というバグを見つけました。
口を閉じ気味にして強く丸めると起きます。放置すると壊れた形のまま比較に出ることになるので直しました。

その結果、方式C の作り直し回数が **3回 / 上限2回** になりました。見た目や品質は一切変えていません。

**決めていただきたいこと。**

| 案 | 帰結 |
| --- | --- |
| バグ修正は数えない | 方式C は 2回 / 2回。**もう作り直せません** |
| 数える（超過を承認） | 方式C に1回分を追加で認める |

**なぜ今決めたいか。** 方式C にはもう1つ、**未確認の問題**があります。
「顔を左右に振ったとき、パーツの間に隙間ができないか」— これはまだ**測っていません**。
実際の映像で問題が出たとき、**直す余地が残っていないと、壊れたまま比較に出すことになります。**

# 第2部 · 私が決めたこと（報告）

技術的な選択です。**あなたが判断する必要はありません。** 結果として何が起きるかだけ書きます。
異論があれば覆してください。

## ⑤ 方式C の描き方 → 自前で描画、輪郭は滑らかに

方式C は「なめらかに変形する2Dの図形」です。これを画像にする方法を選びました。

**決めたこと。** Chrome を使わず、自前の描画処理を書きます。輪郭は**カクカクさせず滑らかに**します。

**理由。** カクカクさせると、それは**描画方法のせいなのに「方式C の限界」と読まれます**。
方式C を不当に悪く見せることになります。また Chrome を使わないことで、① の遮断設定が方式C には不要になります。

**実装への指示:** `p1-c1` は自前ラスタライザを実装し、cage をスプライン補間する。
補間方式は C の宣言された機構の一部として contract に記録する。

## ⑥ 4方式の画面の合わせ方 → 同じ位置・同じ大きさに揃える

4方式はそれぞれ違う座標系を持っています。方式D にはカメラすら入っていません。
このままだと**顔が画面の別々の場所に写り**、「同じところを拡大して見比べる」ができません。

**決めたこと。** 目・鼻・口角の位置を契約として固定し、4方式ともそこに合うようにします。
ズレていたら自動で不合格にします。

**実装への指示:** `p1-i3` が framing ランドマークと許容差を契約に持つ。
E の authored camera も同じランドマークへ落ちるよう構成し、conformance で検査する。
D には render 側から比較カメラを与える。

## ⑦ デバッグ表示 → 方式ごとの内部表示は、横並びにしない

映像とは別に、内部で何が起きているかを表示する版を作ります。
共通の情報（どのテストか、何フレーム目か）は全方式で同じ見た目にして、横並びで比較します。

**決めたこと。** 方式ごとに違う内部情報（C は変形の様子、D は奥行きの順番、E は立体の位置関係）は、
**横並びにはしません。** 比較できないものを並べると「見やすい方が良い方式」と誤読されるためです。

**実装への指示:** 層1（方式非依存）のみ横並び。層2（機構固有）は方式ごとの個別証拠として置く。

## ⑧ 各テストの動きの内容 → 私が作り、実行前にお見せします

6種類のテストの具体的な動き（何フレーム目でどれくらい口を開けるか等）は私が作ります。

ただし、**これを作る人が「あなたが何を見るか」を決めています。** そして映像制作のやり直しは
方式あたり実質1回しかありません。**作ったものは、実行前に平易な言葉と絵でお見せします。**
そこで「これは見たいものと違う」と言っていただければ作り直します。

**実装への指示:** `p1-i1` が制御トラックを起案する。render 開始前に Orbit が平易な要約を提示し、
mi3san の確認を得る。承認は JSON への署名ではなく「見たいものが入っているか」の確認である。
